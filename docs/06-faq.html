Frequently Asked Questions

Clearing up common misconceptions, comparisons, and practical questions about MCP.

Concepts & Comparisons

Isn't MCP just the same as regular tool use / function calling? ▼

This is the most common misconception. Tool use and MCP are complementary, not the same thing.

Tool use (also called function calling) is a capability built into many AI models. It lets the model output a structured signal saying "I want to call this function with these arguments." The tool definitions are schemas you provide in the inference request.

MCP is a protocol for where those tool definitions come from and how the tool executes. Without MCP you would write and maintain the tool schemas yourself. With MCP, an MCP Server provides them — and also handles execution on your behalf.

In short: tool use is a model capability; MCP is an integration standard. They work together.

How is MCP different from calling an API directly? ▼

When you call an API directly, you are responsible for:

  • Writing the tool schema so the AI model knows what the function does
  • Implementing the HTTP call, auth, and response parsing
  • Maintaining that code as the API evolves

An MCP Server wraps the API and handles all three of those things. Your application just needs to connect to the MCP Server — no schemas to write, no API client to implement.

The other key difference is standardisation. Because MCP is a common interface, the same tool discovery and execution mechanism works across every MCP Server, regardless of which API sits behind it.

Is MCP tied to a specific AI model or provider? ▼

No. MCP is an open protocol and is completely LLM-agnostic. Any AI model that supports structured tool calling can work with MCP — whether it is a hosted commercial model or an open-source model running locally.

The MCP Client library handles the communication with MCP Servers; the AI model just receives tool schemas and returns tool-call decisions. Those are independent concerns.

How does MCP compare to OpenAPI / Swagger? ▼

OpenAPI is a specification for describing REST APIs. It defines endpoints, request/response schemas, and authentication — but it does not define how an AI model should discover or call those APIs at runtime.

MCP solves a different problem: it defines a live, runtime protocol that a running AI application uses to discover tools and execute them. An MCP Server could be backed by an OpenAPI-described service, but MCP itself is the real-time communication contract between the AI application layer and the integration layer.

What is the difference between a Tool, a Resource, and a Prompt? ▼
PrimitiveWhat it isWho decides to use it
Tool A callable function with a typed schema — performs an action or retrieves data The AI model (it decides when to call tools based on the conversation)
Resource A URI-addressed, read-only piece of data the AI can fetch The AI model or the host application (explicit fetch)
Prompt A reusable, parameterised prompt template stored on the server The host application (it retrieves and injects prompts as needed)

Practical Questions

Who writes MCP Servers? ▼

Anyone can write an MCP Server. You will encounter three main sources:

  • Official servers from service providers — A cloud platform might release an official MCP Server that exposes their own APIs. This is the highest-quality option because the provider maintains it alongside the API itself.
  • Community-maintained open-source servers — The community often builds MCP Servers for popular tools and platforms. Check that the project is actively maintained before adopting it.
  • Internal / custom servers — Your team can build MCP Servers for internal systems or proprietary data sources. The specification is open and SDKs exist for TypeScript and Python to make this straightforward.
Does an MCP Server have to run as a separate process? ▼

No. While many MCP Servers run as separate processes (especially when using stdio transport), you can also embed an MCP Server in-process with your host application, or connect to a remote MCP Server running on a different machine or cloud service.

For local development, running the server as a subprocess over stdio is the simplest approach. For production, remote servers accessed over HTTP + SSE or WebSockets are common.

How does authentication work with MCP Servers? ▼

MCP itself does not prescribe a specific authentication mechanism — that is left to the implementation. In practice, authentication is handled at two levels:

  • Client-to-server: How your application authenticates with the MCP Server. For local (stdio) servers this is often implicit (same process, same user). For remote servers, API keys, OAuth tokens, or mTLS are common.
  • Server-to-external-service: How the MCP Server authenticates with the external API it wraps. This is entirely the server's responsibility — your application never handles it.
Can I use multiple MCP Servers at the same time? ▼

Yes. A single MCP Client can maintain connections to multiple MCP Servers simultaneously. All the tools from all the connected servers are merged into a single tool list that gets passed to the AI model. The client handles routing — when the AI model calls a tool, the client knows which server to send the request to.

What languages have MCP SDKs? ▼

Official SDKs exist for TypeScript and Python, maintained by Anthropic at github.com/modelcontextprotocol.

Community SDKs are also available for other languages including Go, Rust, Java, and Kotlin. Because MCP is an open specification based on JSON-RPC, you can implement it in any language that can serialise JSON and communicate over the chosen transport.

Is MCP production-ready? ▼

MCP was released in late 2024 and has seen rapid adoption. Major AI development tools, IDEs, and platforms have added MCP support. The specification is versioned and evolving, so check the official changelog for the latest status.

For production use, prefer official or well-maintained community MCP Servers, pin the MCP SDK version in your dependencies, and treat the security boundary between your application and MCP Servers as you would any other external service dependency.
