Transport & Message Types

How MCP clients and servers communicate — transport options, the message lifecycle, and the key message types you need to understand.

Transport agnosticism

One of MCP's most practical design choices is being transport agnostic. This means the protocol does not dictate how messages travel between the client and server — only what those messages contain and what they mean.

The same MCP Server can be reached over stdio (for a local process), over HTTP with Server-Sent Events (for a remote service), or over WebSockets (for a persistent bidirectional connection) — and the application logic stays identical regardless.

Why this matters
You can develop and test an MCP Server locally over stdio, then deploy it as a remote HTTP service without changing the tool logic at all. Only the transport layer changes.

Common transport options

Transport Typical use case Notes
stdio Local MCP Server running as a subprocess Simplest setup; no networking required; ideal for development and CLI tools
HTTP + SSE Remote MCP Server accessed over the network Client sends HTTP POST; server streams results back via Server-Sent Events
WebSockets Persistent, low-latency connections Good for servers that push notifications or have long-running operations
Custom / in-process Server embedded directly in the host process Zero serialisation overhead; useful for testing or tightly-coupled deployments

The wire format — JSON-RPC 2.0

Regardless of which transport is used, all MCP messages are encoded as JSON-RPC 2.0 payloads. JSON-RPC is a lightweight remote procedure call protocol that uses JSON for encoding. It defines a simple structure for requests, responses, and notifications. 

// A JSON-RPC 2.0 request
{
  "jsonrpc": "2.0",
  "id": 1,
  "method": "tools/call",
  "params": {
    "name": "list_repositories",
    "arguments": { "owner": "my-org" }
  }
}

// A JSON-RPC 2.0 response
{
  "jsonrpc": "2.0",
  "id": 1,
  "result": {
    "content": [
      { "type": "text", "text": "[{\"name\": \"my-app\"}, {\"name\": \"my-api\"}]" }
    ]
  }
}

Core message types

The MCP specification defines several message types. The two you will encounter most often are tool discovery and tool execution.

1. Tool discovery — tools/list

Before an AI model can decide which tools to use, the host application needs to know what tools are available. The MCP Client sends a tools/list request; the server responds with a structured list of tool schemas. 

// Request
{ "jsonrpc": "2.0", "id": 1, "method": "tools/list" }

// Response (simplified)
{
  "jsonrpc": "2.0",
  "id": 1,
  "result": {
    "tools": [
      {
        "name": "list_repositories",
        "description": "List all repositories accessible to the authenticated user",
        "inputSchema": {
          "type": "object",
          "properties": {
            "visibility": {
              "type": "string",
              "enum": ["public", "private", "all"],
              "description": "Filter by repository visibility"
            }
          }
        }
      }
    ]
  }
}

2. Tool execution — tools/call

When the AI model decides a tool should be called, the host application asks the MCP Client to execute it. The client sends a tools/call request with the tool name and arguments; the server executes the tool and returns the result. 

// Request
{
  "jsonrpc": "2.0",
  "id": 2,
  "method": "tools/call",
  "params": {
    "name": "list_repositories",
    "arguments": { "visibility": "private" }
  }
}

// Response
{
  "jsonrpc": "2.0",
  "id": 2,
  "result": {
    "content": [
      {
        "type": "text",
        "text": "[{\"name\":\"api-service\"},{\"name\":\"data-pipeline\"}]"
      }
    ],
    "isError": false
  }
}

Additional message types

MCP also defines messages for resources and prompts:

MethodPurpose
tools/listDiscover available tools and their schemas
tools/callExecute a named tool with arguments
resources/listDiscover available resources
resources/readFetch the content of a specific resource
prompts/listDiscover available prompt templates
prompts/getRetrieve a specific prompt template with arguments
initializeHandshake: exchange protocol version and capabilities

Connection lifecycle

Every MCP session follows a standard lifecycle regardless of transport:

  • 1
    Connect

    The client establishes a connection to the server using the configured transport.

  • 2
    Initialize

    Client and server exchange an initialize handshake to agree on protocol version and negotiate capabilities (e.g. which message types each side supports).

  • 3
    Discover

    The client calls tools/list, resources/list, and/or prompts/list to build a picture of what the server offers.

  • 4
    Operate

    The client calls tools and fetches resources as directed by the host application over the lifetime of the session.

  • 5
    Disconnect

    When done, the connection is closed cleanly. For stdio transports this happens when the subprocess exits; for network transports it is an explicit close.

Stateless vs stateful servers
HTTP + SSE transports are typically stateless — each request is independent. stdio and WebSocket transports maintain a persistent session. The MCP specification supports both patterns, so you can choose the right one for your deployment.
