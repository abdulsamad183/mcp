MCP Architecture

A precise breakdown of every component in the MCP ecosystem and how they relate.

The full picture

MCP has a layered architecture. At the top sits the user-facing application; at the bottom sit external services like databases, APIs, and file systems. MCP defines the protocol and roles for everything in between.

Component 1 — The Host Application

The host application is the software your users interact with. It could be:

  • A chat interface powered by an AI model
  • A coding assistant embedded in an IDE
  • An autonomous agent pipeline
  • A customer support tool
  • Any application that needs to give an AI model access to external capabilities

The host application is responsible for the user experience and for deciding when to invoke tools. It does not implement tools directly — it delegates that work to MCP Servers via the MCP Client.

Component 2 — The MCP Client

The MCP Client is a library embedded inside the host application. It acts as the communication bridge between the host and one or more MCP Servers.

Key responsibilities of the MCP Client
  • Establishing and maintaining connections to MCP Servers
  • Sending ListToolsRequest to discover available tools
  • Sending CallToolRequest to execute a specific tool
  • Handling protocol-level details (serialisation, transport, errors)
  • Exposing a clean API to the host application

From the host application's perspective, the MCP Client looks like a simple library call. The host says "give me the available tools" or "run this tool with these arguments" and the client handles everything else.

Component 3 — MCP Servers

An MCP Server is a process or service that exposes tools, resources, and prompts to MCP Clients. Each server typically wraps a single external service or domain.

MCP Servers are the reusable, shareable integration units of the ecosystem. Rather than each application team implementing their own version of a GitHub integration or a database connector, one MCP Server covers that integration for everyone.

🔨

Tools

Functions with typed input/output schemas. The AI model in the host application decides when to call them. Examples: create_ticket(), run_query(), send_email().

📄

Resources

URI-addressed, read-only data that the host or AI model can fetch on demand. Examples: a specific file, a database row, a documentation page.

💬

Prompts

Named, parameterised prompt templates stored on the server. The host application can retrieve them and inject them into AI conversations.

Who builds MCP Servers?

Anyone can write an MCP Server. In practice, you will see three main sources:

SourceExampleTypical quality
Official (service provider) A cloud provider publishing their own MCP Server for their APIs High — maintained alongside the API itself
Community An open-source MCP Server for a popular developer tool Varies — check maintenance activity
Internal / custom Your team building an MCP Server for a proprietary internal system Controlled by you

One client, many servers

A single MCP Client can connect to multiple MCP Servers simultaneously. From the host application's point of view, all the tools from all the connected servers appear as a single unified pool. The host doesn't need to know which server a tool comes from — the client handles routing automatically.

Principle of least privilege
Each MCP Server only exposes what it owns. A calendar MCP Server cannot access your database. This separation keeps the architecture modular and reduces the blast radius of any single component misbehaving.
